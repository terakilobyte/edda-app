EDDA on Linux

Two downloads, one rule. The .deb installs like any package and pulls in what it needs. The AppImage runs anywhere, and carries everything it can: the web view, GTK, the voice engines' runtime. What it cannot carry is the layer that talks to your GPU and kernel, and everything that layer links to. That comes from your distro, and every graphical distro already has it.

If EDDA starts, it works. The requirements below decide whether it starts; nothing about the app is different between distros once it is running.

The .deb (Debian, Ubuntu 22.04+, Mint, Pop!_OS)

sudo apt install ./EDDA_<version>_amd64.deb

It depends on libwebkit2gtk-4.1-0 and libgtk-3-0; apt brings in the rest. Updates arrive through the app.

The AppImage (any distro)

chmod +x EDDA_<version>_amd64.AppImage
./EDDA_<version>_amd64.AppImage

From the system it needs FUSE 2 (to mount itself), GTK 3, GStreamer 1.0 with the base and GL plugins (the web view's media stack), Mesa (GL and EGL) and ALSA. Most desktops have all of it; FUSE 2 is the one that is sometimes missing on newer installs:

  • Ubuntu, Debian, Mint: sudo apt install libfuse2 libgtk-3-0 gstreamer1.0-plugins-base gstreamer1.0-gl libasound2
  • Fedora: sudo dnf install fuse fuse-libs gtk3 gstreamer1-plugins-base alsa-lib
  • Arch, Manjaro: sudo pacman -S fuse2 gtk3 gst-plugins-base alsa-lib

No FUSE and no way to add it? Run it unpacked: ./EDDA_<version>_amd64.AppImage --appimage-extract-and-run.

Why the AppImage isn't fully self-contained

Bundling Mesa breaks GPU acceleration on any machine but the one it was built on, and GStreamer's codec plugins are the host's by design. GStreamer links glib, so glib and everything glib links against have to be the host's too: one family, one machine. Version 0.3.0's AppImage broke that rule halfway (the host's glib, a bundled libmount) and failed to start on newer distributions with version 'MOUNT_2_40' not found; 0.3.1 fixes it.

Journals under Proton and the HUD under Wayland

EDDA reads the game's journal from the Proton prefix automatically. The HUD overlay is an always-on-top window; under Wayland some compositors will not let a window stay on top, in which case the HUD shows as a normal window you can keep beside the game. The galaxy-map automation types into the game through uinput, which needs your user in the input group on most distributions.

Something else in the way? Report it with your distribution and the terminal output; the first line usually names the library.
